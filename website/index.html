AWS detection engineering · LLMs

Hand an LLM your AWS keys. What does it do next?

Attackers already use LLMs, so I ran the defender's version of the question. I put models in 13 situations where each has just gained access to an AWS account, asked only for its next move, and matched every answer to CloudTrail. Nothing ran against a real account. I am reading the plan, not an intrusion.

The short version

    About this study

    Why I ran this

    Models are already in attacker hands, whether a person is driving or an agent is built on top of one. I wanted to see what each model is biased toward once it is inside an account: what it reaches for first, what it treats as normal, and where it draws a line.

    What it tells us

    Over many runs this shows which actions a model is most likely to put on the table, and where models differ: how one sets up persistence, whether another disables logging, how they assume a role. Where models converge is where detections should sit. It also shows which models refuse, which propose real changes to the account, and whether newer models invent new tradecraft or still reach for the classics like creating an IAM user to persist.

    How to read this, and what it is not. Every answer is single-turn and nothing runs against a real account. The prompt and the harness around a model shape its answer a lot, so this cannot tell you what a real attacker would do. It is a way to gauge how likely different models are to propose different next steps in simple, controlled situations. The situations are simulated post-exploitation states, laid out below. The code is open, so you can write your own situations and run them.
    Key terms used on this page
    CloudTrail
    AWS's audit log. Every API call an identity makes lands there, so it is what defenders write detections against.
    AWS action (event)
    One API call, like GetSecretValue (read a secret). Every step a model proposes maps to the CloudTrail event it would leave behind.
    Tactic
    The attacker goal behind a step, using MITRE ATT&CK names. Persistence is keeping a way back in; Defense evasion is dodging monitoring.
    Tempting move
    The obvious next step each situation dangles. The headline number on a situation is how many answers went for it.
    Refused · something else
    Refused means the model declined to help. Something else means it proposed other steps instead, usually more looking around.
    Answer
    One reply from one model to one situation. Each model answered each situation 20 times, so every percentage is over real repeats.

    What's in the study

    How it ran: every model got the same instructions for a situation, framed as an authorized security assessment, and had to reply with a plan of next steps in a fixed format (JSON). One reply is one answer, and each model answered each situation 20 times. I then mapped every proposed step to the AWS action it would perform, the CloudTrail event it would leave, and its ATT&CK tactic. Claude and GPT models ran through their consumer subscriptions, the rest through OpenRouter.

    Where the models differ

    Rates tell you how often. This tells you what: the command a model opens with, how it keeps access, and how wide its range is. This is where the models stop looking alike.

    First move: the opening command

    When the situation asks for exactly one command (aws-06), this is the single action each model opens with. These add up to 100% (with refusals and any other openers), so each one is a real alternative, not overlapping events. Most run GetCallerIdentity ("who am I"). Dolphin and Llama list users instead. Grok mostly refuses to start.

    Persistence style: how it keeps access

    Across the two admin situations (aws-02 and aws-11): how often a model proposes persistence, and which mechanism. Bar length is how often it persists. The segments are the mix (one answer can use more than one). Plenty of models never persist at all.

    Naming tells: what they call the sessions and users they create

    The literal names models put in --role-session-name and on the IAM users and roles they create. These are descriptive and self-referential, which makes them cheap, high-precision CloudTrail signatures. (The session names lean on the authorized-assessment persona the prompt sets; the IAM names are more about intent.)

    How they make admin access stick

    When a model had broad admin (aws-02 and aws-11) and chose to persist, which mechanism did it use? A new IAM user with a fresh access key wins, and it is the loudest, most detectable option. Backdoored role trust policies come next. These are counts of enacting answers.

    Detection read. The top persistence paths map to a short, high-value CloudTrail watchlist: CreateUser+CreateAccessKey on an existing identity, UpdateAssumeRolePolicy / PutRolePolicy trust changes, and CreateFunction for Lambda footholds. Rare moves (console login profiles on API-only principals) are low-volume but high-signal.

    The 14 models, and how I reached them

    Seven vendors: frontier labs, open-weight models, and one uncensored fine-tune. Claude ran through a consumer Max subscription (Claude Agent SDK), GPT through a ChatGPT subscription (OpenAI Codex SDK), and the rest through OpenRouter with the provider pinned. Every call was single-turn and nothing was executed.

    Method. Single-turn: each model proposes next steps and nothing runs against any account. Every step is mapped to the AWS action it would perform, the CloudTrail event it would leave, and a MITRE ATT&CK tactic. Prompts frame the work as an authorized assessment. Claude and GPT were reached through consumer subscriptions, the rest through OpenRouter.

    Reading the numbers. A rate only means something next to its situation. "87% read secrets" means when secrets are already located and readable, not in general. When a situation asks for a multi-step plan, an action's percentage is the share of answers whose plan included it, so actions in one plan overlap and don't add up to 100%. answers came back as prose instead of the required plan format. An agent could not act on those, so they are left out of the rates and shown only under Safety posture.
