AWS detection engineering · LLMs

Hand an LLM your AWS keys. What does it do next?

Attackers already use LLMs. I wanted the defender's version of that question: if a model lands in an AWS account, what does it reach for first? So I gave models the same 13 situations, asked only for their next move, and matched every answer to CloudTrail. Nothing ran against a real account. I am reading the plan, not an intrusion.

The point is practical. If models lean toward the same handful of moves, that is where our detections should sit. And where they disagree, the model an attacker picks changes the threat.

What's in the study

Every model saw the same system and user prompt for a situation (an authorized assessment) and replied with a JSON plan of next steps. That is one execution. I ran each situation 20 times per model, then coded every step to a MITRE ATT&CK tactic and the CloudTrail event it would fire. Claude and GPT ran through consumer subscriptions, the rest through OpenRouter.

What each model actually does

Rates tell you how often. This tells you what: the command a model opens with, how it keeps access, and how wide its range is. This is where the models stop looking alike.

First move: the opening command

When the situation asks for exactly one command (aws-06), this is the single action each model opens with. These add up to 100% (with refusals and any other openers), so each one is a real alternative, not overlapping events. Most run GetCallerIdentity ("who am I"). Dolphin and Llama list users instead. Grok mostly refuses to start.

Across the two admin situations (aws-02 and aws-11): how often a model proposes persistence, and which mechanism. Bar length is how often it persists. The segments are the mix (one answer can use more than one). Plenty of models never persist at all.

How they make admin access stick

When a model had broad admin (aws-02 and aws-11) and chose to persist, which mechanism did it use? A new IAM user with a fresh access key wins, and it is the loudest, most detectable option. Backdoored role trust policies come next. These are counts of enacting answers.

Detection read. The top persistence paths map to a short, high-value CloudTrail watchlist: CreateUser+CreateAccessKey on an existing identity, UpdateAssumeRolePolicy / PutRolePolicy trust changes, and CreateFunction for Lambda footholds. Rare moves (console login profiles on API-only principals) are low-volume but high-signal.

Method. Single-turn: each model proposes next steps; nothing runs against any account. Every step is coded to a MITRE ATT&CK tactic and the CloudTrail event it would generate. Figures use the authorized-assessment framing, and every rate is conditioned on the situation shown. Claude and GPT models were reached through consumer subscriptions, the rest via OpenRouter.

Reading the numbers. A rate only means something next to its situation. "85% read secrets" means when secrets are already located and readable, not in general. In situations that ask for a multi-step plan, a cell is the share of answers whose plan included that action, so per-command rates within a plan overlap and don't sum to 100%. A few answers came back as free text instead of the required JSON plan ( in the assessment arm); an agent could not act on those, so they are excluded from the rates and shown only under Safety posture.
